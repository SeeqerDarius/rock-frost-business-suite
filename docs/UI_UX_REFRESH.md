## Product direction

Rock Frost should remain restrained and operational, but it must no longer look like an unbranded neutral template. The RF blue is a semantic accent for active navigation, primary actions, focus, KPI emphasis, and selected states. It is not a decorative gradient or a replacement for the neutral information hierarchy.

## Sidebar behavior

- Desktop navigation is persistent and user-collapsible.
- The collapsed state preserves icon navigation, active-state visibility, accessible labels, and tooltips.
- The preference is saved locally and restored after hydration.
- Mobile navigation remains a modal sheet with full labels and closes after route selection.
- The active route uses both shape and RF-blue contrast; color is not the only active-state signal.
- The collapse control remains keyboard accessible and clearly communicates the resulting state.

## Dashboard hierarchy

Hotel and School overviews are operational landing pages, not collections of identical cards. Their first row presents real headline metrics with direct navigation. A secondary workflow panel exposes the module's most frequent tasks and the most important operational domains without fabricating data.

## Acceptance criteria

1. Sidebar expands/collapses without hiding navigation access or breaking mobile navigation.
2. Active routes remain obvious in light and dark themes.
3. At 1024px and above, the content area gains usable width when the sidebar is collapsed.
4. Hotel and School overview cards are fully clickable, keyboard focusable links with descriptive labels.
5. The implementation uses semantic tokens and Lucide icons, with no gradients, glassmorphism, or invented metrics.
6. Lint, strict TypeScript, unit tests, and the production build pass before release.

## Claude review lane: findings (2026-08-03)

Reviewed against commit `fa5494f` ("Refine workspace navigation and module UX") without editing any Codex-owned file (`app-shell.tsx`, `sidebar-nav.tsx`, `active-navigation.ts`, Hotel/School overview pages). No code was changed in this pass; findings are proposed follow-ups.

**Interaction model (`AppShell`/`SidebarNav`) — sound overall.** Segment-boundary active matching, collapsed-state tooltips, and the mobile sheet all behave as specified in the acceptance criteria above. Two follow-ups, neither blocking:
1. `OrganizationSwitcher` is only rendered when the sidebar is expanded (`app-shell.tsx:80`). A multi-org user who collapses the sidebar loses the switcher entirely, with no icon-only fallback or access via `UserMenu`. Worth a small follow-up so multi-org accounts always have a switch affordance.
2. The collapsed/expanded preference intentionally restores from `localStorage` after hydration (`getServerSidebarPreference` always returns `false`), which is documented above as by-design. This does mean a user who left the sidebar collapsed sees one visible expand-to-collapse flash on every full page load. If that's ever worth eliminating, the standard fix is a cookie + a small blocking inline script (the pattern `next-themes` uses for dark mode) rather than `localStorage` alone — no action needed now, just noting the mechanism for later.

**Public acquisition pages — consistent, nothing broken.** Home, Solutions, Modules, Industries, Company, and Contact all share the same `Card`/section rhythm and `moduleRegistry`-driven content, so there's no drift between them. One polish gap: `PublicHeader`'s nav links (`public-header.tsx`) have no active-route styling, unlike the authenticated sidebar's deliberate shape+color active state. Low priority, but it's the one place the public site reads as less finished than the authenticated shell.

**Consent-controlled customer showcase.** The home page includes a responsive customer-story carousel only when at least one eligible organization exists. Eligibility is intentionally strict: the organization must be `ACTIVE`, have an uploaded logo, have complete quote/attribution copy, and be explicitly enabled by a platform operator from the organization detail page after marketing permission is obtained. Onboarding alone never publishes a tenant. The carousel uses accessible selection buttons and previous/next controls without forced automatic rotation, and it never fabricates fallback testimonials. Approved base64 logos are served through a separately guarded, cacheable public image route rather than serialized into the home-page React payload.

The same carousel also accepts explicitly published independent customers managed from Platform Settings. The owner can control section visibility and copy, industry display, logo uploads/replacement, customer copy, publish state, and ordering. Platform Settings is separated at the bottom of the platform sidebar; the avatar menu's Profile settings destination remains personal account management.

**Revised (2026-08-11) — card redesign, carousel behavior, and demonstration entries.** The showcase previously rendered as one large hero panel (a full-height dark logo panel beside a quote panel) plus a row of small logo "switcher" thumbnails below it — functional, but visually heavy with a lot of empty space and no consistent card language. `src/components/marketing/customer-showcase.tsx` was rebuilt around a proper card carousel:

- Each customer is a self-contained card: a bounded, consistently-sized logo frame (`object-contain`, soft `bg-muted` background, subtle border — works for both a wide wordmark and a square mark without awkward cropping or oversized empty space), name/industry, a clamped-width quote that wraps naturally instead of truncating mid-sentence, and an attribution footer pinned to the bottom of the card via flex so cards of differing quote length still line up in a row.
- Logos load into a skeleton-pulse placeholder rather than an empty box (real uploaded logos can be sizeable; the frame reserves its full space immediately so nothing shifts once the image arrives) and fall back to a deterministic colored initials mark — never a broken-image icon — if the source is missing or fails to load.
- The carousel itself is a CSS scroll-snap track (1 card + a peek of the next on mobile, ~2 on tablet, ~3 on desktop) rather than a JS-transform slider: this gets native touch/trackpad scrolling, no measured-layout-shift risk, and `prefers-reduced-motion` support for free from the app-wide rule in `globals.css` that already forces `scroll-behavior`/animation durations to ~0 — no separate `motion-safe:`/`motion-reduce:` handling was needed. Previous/next buttons, a small per-card position-dot row, and keyboard arrow/Home/End support all drive the same native scroll position. There is deliberately no autoplay, continuing the existing "without forced automatic rotation" decision above rather than revisiting it.
- **Fictional demonstration entries** (`src/lib/demo-showcase-customers.ts`) now exist to keep the section looking intentional before enough real customers are approved — every demo card carries a visible "Sample" badge, and a disclosure sentence appears whenever one is shown. Real approved entries always come first and are never displaced; demo entries only fill the gap up to a small minimum and disappear automatically once real approvals reach it. Full rules in `docs/PLATFORM_SETTINGS.md`'s "Demonstration showcase entries" section.

**Fixed (2026-08-11) — logos permanently stuck on the empty skeleton in production.** `LogoFrame`'s load state relied only on the `<img>`'s `onLoad`/`onError` React handlers, which is vulnerable to a hydration race: a fast, same-origin, often-cached logo (exactly what the demo SVGs and any previously-loaded real logo are) can finish loading before React attaches those listeners during hydration, so the state never leaves `"loading"` and the real image stays hidden behind the skeleton forever. Fixed by adding a `useEffect` that checks the `<img>`'s `.complete`/`naturalWidth` once on mount and resolves state immediately if the image had already finished loading by then — see `OPERATOR_HANDOFF.md`'s 2026-08-11 fix entry for the full root-cause writeup and production verification.

**Small-format RF icon treatment — the real finding.** The RF mark is inconsistent across the icons actually in use:
- `src/app/icon.png` (the browser-tab favicon, and also the literal image `Logo` renders at 30x30px in every sidebar/header instance across the whole app) uses a flat mark on a light background.
- `src/app/apple-icon.png` and `public/icon-192.png`/`icon-512.png` (PWA/iOS home-screen icons, declared in `public/manifest.webmanifest`) use a different, more polished treatment: a chrome/gradient RF mark on a dark-navy rounded-square backdrop that matches the manifest's `background_color: "#020306"` / `theme_color: "#08b2ec"`.
- Because `icon.png` has a light background baked in, it renders as a bright white square inside the dark sidebar in dark mode (`.dark`'s `--sidebar: oklch(0.205 0 0)`), clashing with the rest of the chrome.
- `public/rf logo.png` — a higher-fidelity chrome RF mark, no baked-in background — has zero references anywhere in `src/`. It's an orphaned asset, and its filename contains a literal space, which would need encoding if ever linked directly.
- The JSON-LD `Organization.logo` in `src/app/(public)/layout.tsx:17` points at `public/RFG.png`, a decorative mascot/poster illustration with a baked-in tagline ("Turning ideas into infinite possibilities"), not a square brand mark. That doesn't fit Google's structured-data logo guidance and may hurt rich-result eligibility.

**Applied (2026-08-03, on explicit request):** `src/app/icon.png` is now a copy of `apple-icon.png` (180x180, same dark-navy chrome mark), so the favicon, in-app `Logo` instances, and PWA icons are one consistent asset. # Visible authenticated navigation feedback

The authenticated root does not use a root `app/loading.tsx` fallback because that boundary can replace the complete workspace while a route suspends, making the sidebar and current page appear to blank out. `AppNavigationLoader` (`src/components/feedback/app-navigation-loader.tsx`) instead keeps the current workspace mounted and places only the original pulsing round RF indicator above it until the real pathname/search parameters change. There is no opaque background, progress bar, card, or “Loading workspace” copy. External/new-tab/download/same-page interactions are excluded, and the app-wide reduced-motion policy applies.

The navigation transition deliberately keeps the current workspace visible: a slim top progress line and a compact glass status pill float above the existing page instead of an opaque full-screen replacement, avoiding a blank/disappear/reappear effect while still blocking accidental repeated navigation during the transition.

**Revised (2026-08-10) — the original version had two real problems, not just a look-and-feel issue:**

1. **The overlay's visible duration was a blind `setTimeout(650ms)`**, unrelated to when the navigation actually finished. A fast prefetched route (the common case) still showed "loading" for the full 650 ms after the new page had already rendered underneath it; a genuinely slow route (a cold data fetch) lost its loading feedback at the 650 ms mark even though the page was still loading. Fixed by tracking the real `usePathname()`/`useSearchParams()` change as the completion signal, with a small minimum-visible time (260 ms, so instant navigations don't flash) and a safety ceiling (8 s, so a hung request can't leave the click-blocking overlay stuck).
2. **The progress bar didn't progress** — a bar frozen at a fixed 50% width, opacity-pulsing in place, doesn't read as "in progress" to a user; it reads as broken or stalled. It now genuinely animates: width eases up toward ~86% while waiting, then completes to 100% only once real navigation completion fires, via a CSS width transition rather than an opacity pulse.

The navigation indicator uses the original `animate-ping`/`animate-pulse` RF treatment requested by the product owner. The temporary top progress bar, status pill, workspace card, and explanatory copy were removed.

**Updated 2026-08-23 (explicit product-owner request) — compact lockup swapped from `RFGgg.png` to `rft.png`.** The line above and the "approved alternate" note further down originally described `RFGgg.png` (a single-line wordmark, 1015×129, no subtitle) as the only asset light enough for the compact animated `Logo` component, with the taller "Technologies"-subtitle treatment reserved for the larger `rfggggg.png` marketing lockup. Verified at both the compact (`h-4`) and default (`h-6`) container sizes in a real browser at true desktop (1280px) and mobile (375px) viewport widths — the "TECHNOLOGIES" subtitle renders small but legible at `h-6`, and there is no overlap with adjacent header content (Sign in / Subscribe) at either width; a `getAnimations()` check confirmed the shimmer sweep is still running and the mask is still correctly clipped to the new file's shape. `RFGgg.png` and `rfggggg.png` remain on disk, now unreferenced by any component — left in place rather than deleted, since removing an asset wasn't asked for and another surface may still expect it.

**Sized up 2026-08-23 (same day, explicit product-owner follow-up) — default container bumped from `h-6` to `h-7`.** At the shared `h-6` (24px) container both old and new files were fit to, `RFGgg.png`'s wordmark filled the box edge-to-edge (its 129px-tall file has no subtitle), while `rft.png`'s "ROCK FROST" wordmark only occupies the top ~129 of its 180px-tall file — object-contain scales the whole file to the container height, so the wordmark itself rendered at only `24 × (129/180) ≈ 17px`, about 72% of the old apparent size. The owner asked for it closer to the old size, "about 85% close." Solving `h × (129/180) = 0.85 × 24` gives `h ≈ 28.5px`; the closest value on Tailwind's default scale is `h-7` (28px), which yields `28 × (129/180) ≈ 20px`, or about 84% of the old size — verified in a real browser via the same `getBoundingClientRect()` method as the swap note above: renders at 157.9×28 (well under the unchanged `max-w-[188px]` cap, so no overflow), with a 4px gap to "Sign in" at 375px mobile width (down from ~27px at `h-6`, tighter but not overlapping) and comfortable spacing at 1280px desktop. `compact` (collapsed-sidebar, `h-4 max-w-12`) was deliberately left unchanged — it's width-constrained by `max-w-12` regardless of height on either file, so both old and new already rendered as an effectively illegible ~6-8px mark there; changing its height wouldn't have moved that size at all.

**Ambient shimmer (2026-08-13, explicit product-owner request).** The wordmark now carries a continuous, low-frequency light sweep — a bright diagonal band crosses the lettering roughly every 4.5 seconds and is otherwise still. This is a deliberate exception to this document's general "no gradients used decoratively" restraint: the owner was shown three more restrained alternatives (one-time entrance, hover-only, animation confined to the auth screen) and explicitly chose the always-on ambient loop. Implementation is `.logo-shimmer` / `.logo-shimmer-band` in `src/app/globals.css`, consumed by `src/components/layout/logo.tsx`, so it applies everywhere the shared `Logo` component renders (public header, authenticated app shell, auth pages) without each call site doing anything extra. Two things worth knowing if this is ever touched again:

- The mask (`mask-image`/`-webkit-mask-image` pointing at `/rft.png`, see the 2026-08-23 swap note above) clips the shimmer band to the wordmark's own alpha shape — it lives on the static wrapper element, never on the element whose `transform`/`background-position` is animated. Animating `background-position` directly on a masked element was tried first and silently stopped repainting per frame in Chromium (confirmed by hand: a static masked fill renders correctly, the same element with an animated `background-position` under the same mask does not, even though every computed style reports the animation as "running"). The band is a separate plain child animated with `transform: translateX(...)` only, which is compositor-driven and doesn't hit this — masking stays static, animation stays on an unmasked-by-itself child that inherits the parent's mask via normal painting.
- Verifying this kind of animation by pausing it and then changing `animation-delay` does **not** retroactively seek it — a paused CSS animation stays frozen at whatever moment it was paused, regardless of later delay changes. To force an exact frame for a screenshot, seek the real animation via the Web Animations API instead: `element.getAnimations()[0].currentTime = ms`.

Respects the app-wide `prefers-reduced-motion` rule in `globals.css` like everything else — under reduced motion the sweep's `animation-duration` collapses to ~0 and it reads as a static wordmark.

The larger transparent `public/rfggggg.png` artwork is retained as an approved alternate marketing wordmark with the “Technologies” and further tagline-sentence treatment, distinct from `rft.png`'s wordmark-plus-subtitle-only version now used in the compact `Logo` component. `rfggggg.png` itself is not used in compact application navigation, favicons, PWA icons, or loading indicators.
